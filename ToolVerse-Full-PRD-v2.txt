====================================================================== 1.
PROJECT OVERVIEW
======================================================================

1.1 Vision ToolVerse is a responsive, mobile-first website that provides
useful browser-based tools in one place. Visitors can discover tools,
search and filter them, open each tool, and use it without creating an
account. An admin area manages tool metadata, sections, and site
settings through a transparent static-hosting workflow.

1.2 Primary goals - Provide a fast, usable, accessible online tools
directory. - Ensure every listed tool performs its stated function; no
fake buttons or UI-only demos. - Maintain a consistent design system
across public pages, tool pages, and admin pages. - Keep the tool
registry and section/category references synchronized. - Allow tools to
be added one at a time without breaking existing tools. - Make local
draft, export, and deployment states explicit. - Provide understandable
validation, errors, success messages, and recovery paths. - Deploy by
uploading static files to InfinityFree. - Deliver maintainable source
code and test documentation.

1.3 Non-goals - No public accounts or server-side user profiles. - No
server-side database or backend API. - No server-side file editing from
browser JavaScript. - No claim of secure server-side admin
authentication. - No simulated successful server uploads. - No mandatory
build step, package installation, or compilation.

2. MANDATORY TECHNOLOGY AND HOSTING CONSTRAINTS
======================================================================

2.1 Allowed - HTML5 - CSS3 - Vanilla JavaScript (ES6+) - JSON files for
static configuration and tool registry - Browser-native APIs - Existing
lightweight client-side libraries only when essential, documented, and
compatible with static hosting

2.2 Prohibited - PHP - Node.js or server-side JavaScript - React, Vue,
Angular, or other frontend frameworks - TypeScript build requirements -
MySQL, PostgreSQL, or any database - Firebase or Supabase - Google Apps
Script - External backend services - Mandatory npm, bundling,
compilation, or development server

2.3 Hosting - The project must run after static files are uploaded to
InfinityFree. - The public root is commonly htdocs/. - The canonical
public tool registry should be data/tools.json unless the inspected
project defines another source of truth. - Never use localhost URLs or
development-machine file paths. - Verify .htaccess behavior instead of
assuming all directives are supported. - Document exact upload
destinations, cache troubleshooting, smoke tests, and rollback. -
Relative paths must work from root and nested pages.

2.4 Browser support - Support current stable desktop and mobile
browsers. - Feature-detect Canvas, File, Blob, URL.createObjectURL,
Clipboard, and other APIs before use. - Show graceful messages if an API
is unavailable. - Never silently fail when a required capability is
missing.

8. IMAGE RESIZER — DETAILED PRODUCT REQUIREMENTS
======================================================================

Tool name: Image Resizer Expected path in the current project:
tools/image/image-resizer.html Purpose: Resize an image entirely in the
user’s browser and export the resized result without uploading the image
to a server.

8.1 Upload and input - Support file picker upload. - Support
drag-and-drop where implemented. - Accept common browser-decodable image
formats. - Validate that a selected file is an image. - Handle
corrupted, unsupported, or undecodable files gracefully. - Show a
readable error when the file cannot be loaded. - Do not upload the image
to any server. - Show the selected file name and original dimensions
when available. - Release old object URLs when replacing or clearing an
image.

8.2 Preview - Show an original image preview. - Show a resized output
preview after a successful resize. - Show original and output
dimensions. - Show original and output file sizes where available. -
Keep images contained within the layout without distorting the
preview. - Distinguish the source image from the generated result. -
Show an empty state before an image is selected.

8.3 Dimensions and aspect ratio - Provide custom width and height inputs
in pixels. - Validate positive integer dimensions. - Reject zero,
negative, NaN, infinite, or impractically large dimensions. - Provide a
lock/unlock aspect ratio control. - When locked, changing one dimension
recalculates the other using the original image ratio. - When unlocked,
permit independent dimensions and explain that output proportions may
change. - Avoid unexpected resizing loops or input jitter. - Preserve
original dimensions as a reset option. - Provide a reset dimensions
action. - Recalculate output only when the user requests resizing or
when the established UI behavior explicitly requires live preview.

8.4 Output formats - Support PNG, JPEG/JPG, and WebP where the browser’s
Canvas implementation supports the requested format. - Check the actual
output MIME type returned by canvas.toBlob; do not assume the browser
supports WebP merely because it was selected. - If a format is
unsupported, display a clear error or offer a deliberate fallback. - Use
correct file extensions matching the actual output MIME type. - Do not
label a PNG output as WebP or JPEG. - Use a quality control for lossy
formats such as JPEG and WebP. - Do not imply quality changes
meaningfully affect lossless PNG. - For JPEG, provide a configurable
background color because JPEG does not preserve transparency. -
Composite transparent source images against the chosen background when
exporting to JPEG. - Preserve transparency for PNG and supported WebP
output. - Do not mutate the original file.

8.5 Resize processing - Decode the source image safely. - Check that
Canvas and a 2D context are available. - Guard against excessive
dimensions and canvas allocation failures. - Draw at the requested
dimensions. - Use canvas.toBlob where available to avoid unnecessary
large base64 strings. - Handle null blobs and asynchronous errors. -
Provide a visible processing state if operations take noticeable time. -
Disable conflicting actions while processing where needed. - Clean up
temporary canvas/object URLs at the correct time. - Do not revoke a
download URL before the browser has had a reasonable opportunity to
start the download.

8.6 Download - Provide a clear Download Image action. - Use a meaningful
filename derived from the source filename, such as
name-resized-800x600.webp. - Ensure the extension matches the output
format. - Do not report a successful download if image generation
failed. - Handle unsupported download behavior with a helpful message. -
Keep all processing local to the browser.

8.7 Accessibility and responsive design - All fields must have labels. -
Aspect ratio state must be understandable to screen readers. - Status
and error messages should use an appropriate aria-live region. -
Keyboard operation must be supported. - Visible focus styles are
required. - Buttons must have clear names. - The layout must work on
narrow mobile screens and desktop. - No essential action may be
available only on hover.

8.8 Image Resizer acceptance tests - Upload a valid PNG and resize it. -
Upload a valid JPEG and resize it. - Upload WebP if supported by the
browser. - Reject a non-image file. - Handle a corrupted image. - Change
width with ratio locked and verify height updates. - Unlock ratio and
independently change width/height. - Reject invalid dimensions. - Export
PNG and verify output type. - Export JPEG with transparent input and
confirm background fill. - Export WebP and verify actual output MIME
type. - Test quality control for lossy formats. - Replace an image
repeatedly without leaking old object URLs. - Clear and reset the
tool. - Test a large image and confirm a graceful error if the browser
cannot allocate the canvas. - Test keyboard accessibility and mobile
layout. - Verify no image data is sent to a server.

Do not claim these tests passed unless they were actually run.

10. DRAFT, EXPORT, PUBLISH, AND DEPLOYMENT STATES
======================================================================

Clearly separate: 1. Hosted manifest: JSON served by the website. 2.
Local draft: changes stored in this browser. 3. Exported manifest:
downloaded JSON file. 4. Deployed manifest: version uploaded to the host
and verified.

10.1 Local draft - Use a versioned, namespaced localStorage key. -
Validate stored drafts before restoring. - Handle corrupt/unavailable
storage. - Preserve the last valid manifest. - Show unsaved changes and
saved timestamp. - Provide explicit Save Draft and Discard Draft. - Do
not silently restore stale drafts over newer hosted data. - Detect
conflicts where practical. - Provide deliberate recovery.

10.2 Publish workflow - Provide a dedicated Publish Changes page. -
Summarize pending changes. - Validate the full manifest. - Identify
invalid IDs, missing sections, and missing tool paths where checkable. -
Export valid JSON. - Give exact hosting destination:
htdocs/data/tools.json. - Explain upload/replace using InfinityFree File
Manager or FTP. - Provide a verification action or manual verification
instructions. - Use honest states: Local Draft, Ready to Export,
Awaiting Upload, Verified Deployed Version. - Never claim that local
storage writes to the server.

A static browser app cannot overwrite InfinityFree server files without
a supported server-side or external publishing mechanism. Do not invent
one.

11. IMPORT, EXPORT, BACKUP, AND RESTORE
======================================================================

Export: - Export valid UTF-8 JSON. - Use a meaningful filename. -
Preserve all supported fields. - Block export when required validation
fails. - Do not export credentials or secrets.

Import: - Select a JSON file. - Parse and validate before modifying
current state. - Reject malformed JSON and incompatible schemas. -
Detect duplicate IDs and missing section references. - Show errors and a
summary before replacement. - Preserve a recoverable backup. - Do not
alter current data if validation fails. - Prevent accidental loss of
local drafts.

Backup/restore: - Download backup. - Restore valid backup. - Clearly
distinguish restore, merge, import, and replace. - Never silently
destroy current data.

15. SECURITY AND PRIVACY
======================================================================

Audit: - Hardcoded passwords - Credentials in JS or JSON - Sensitive
localStorage values - Unsafe innerHTML usage - Imported JSON
validation - Path traversal - Dangerous URL schemes - Unnecessary
third-party scripts - Exposure of admin-only controls - Unsafe new-tab
links - Misleading authentication claims

Use textContent or safe DOM construction for untrusted content. Reject
path traversal and unintended external paths. Use rel=“noopener
noreferrer” for suitable new-tab links.

A client-side login is not secure server-side authentication and cannot
protect public static admin files from a determined visitor. Do not
claim production-grade authentication. Do not add a backend to solve
this.

Image privacy: - Image Resizer processing must remain local to the
browser. - Do not upload images to a remote service. - Do not transmit
image bytes to analytics or third-party services. - Document any remote
library dependency honestly.
